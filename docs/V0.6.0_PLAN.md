# v0.6.0 "Diagnostic-First Intelligence" Plan

**Status**: Planning  
**Target**: TBD  
**Focus**: Actionable diagnostic panel based on principles

---

## Vision

Apply "5-Second Rule" to diagnostic panel: Operator should decide on action within **5 seconds** of viewing the panel.

### Core Principles (from LESSONS-LEARNED.md)

1. **"Show, Don't Ask"** - Display relevant information automatically
2. **"Truth Only™"** - Never show fake or misleading data
3. **"Maximum Information Extraction"** - Use all available bundle data
4. **"r8s interprets, user acts"** - Provide intelligence, not just information

## Phase 1: Diagnostic Panel Tightening

### Goals
- Remove noise/fluff from diagnostic panel
- Focus on ONLY actionable information
- Apply "5-Second Rule" - quick decision-making

### Changes

#### REMOVE: External Tools Section
**Current**: 🛠️ EXTERNAL TOOLS shows lnav and kubectl hints  
**Problem**: Not actionable in bundle mode, adds clutter  
**Solution**: Move to help modal ('?' key)  
**Impact**: One less section, tighter panel

#### SHOW ONLY: Failing Containers
**Current**: Shows ALL containers (healthy + failing)  
**Problem**: Healthy containers add noise  
**Solution**: Show only containers with issues  
**Format**:
```
━━━ FAILING CONTAINERS ━━━
❌ main-container: BackOff (x47) - CrashLoopBackOff
❌ sidecar: ImagePullBackOff - registry auth failed
```

#### SHOW ONLY: Warning Events
**Current**: Shows Normal + Warning events mixed  
**Problem**: Normal events ("Started", "Pulled") add noise  
**Solution**: Show only Warning events (unless none exist)  
**Format**:
```
━━━ WARNING EVENTS ━━━
⚠️ BackOff: Back-off restarting failed container (x47)
⚠️ Failed: Image pull failed - registry.example.com [truncated]
```

#### TRUNCATE: Event Messages
**Current**: Full event messages can span multiple lines  
**Problem**: Hard to scan, breaks "5-second rule"  
**Solution**: Truncate at 80 chars + "(truncated)" indicator  
**Impact**: More scannable, consistent line heights

#### NUMBER: Action Suggestions
**Current**: Bullet list of actions  
**Enhancement**: Number them for quick reference  
**Format**:
```
━━━ ACTIONS ━━━
1. Check container logs for exit reason
2. Verify registry credentials (imagePullSecrets)
3. Review resource limits if OOM suspected
```

### New Panel Layout (5-Second Format)

```
━━━ DIAGNOSIS ━━━
🔴 CRASH LOOP - Container failing to start (47 restarts)
   → Check container exit codes in events below

━━━ FAILING CONTAINERS ━━━
❌ main-container: BackOff (x47) - CrashLoopBackOff  
❌ sidecar: ImagePullBackOff - registry auth failed

━━━ WARNING EVENTS ━━━
⚠️ BackOff: Back-off restarting failed container (x47)
⚠️ Failed: Image pull failed - registry.example.com [truncated]

━━━ ACTIONS ━━━
1. Check container logs for exit reason
2. Verify registry credentials (imagePullSecrets)  
3. Review resource limits if OOM suspected

[l]=logs  [Ctrl+P]=previous  [Esc]=back
```

### Implementation Checklist

- [ ] Move External Tools section to help modal
- [ ] Filter containers to show only failing ones
- [ ] Filter events to show only Warning type
- [ ] Add event message truncation at 80 chars
- [ ] Number action suggestions

## Phase 2: Cluster Events Drill-Down (v0.5.9 Known Limitation)

### Problem Discovered in v0.5.9 Testing

**Issue**: Dashboard shows aggregated cluster events (e.g., "190× BackOff", "118× Failed") but provides no way to see which pods are affected.

**Root Cause**: v0.5.9 removed the expansion feature (►/▼ indicators) that showed affected pod lists. This was intentional to simplify navigation, but created a gap for cluster event navigation.

**Current Behavior**:
```
WARNING:
6. 🔴 190× BackOff    Warning events    cluster     <-- Enter does nothing useful
7. 🔴 118× Failed     Warning events    cluster     <-- No way to see pod list
```

**Expected Behavior**: Pressing Enter on cluster event items should show which pods are affected.

### Solution: Cluster Events Diagnostic Panel

Create a new diagnostic panel type for cluster-wide events that shows affected pods.

**New Panel Layout**:
```
━━━ CLUSTER EVENT: BackOff ━━━
⚠️ 190 occurrences across 12 pods

━━━ AFFECTED PODS ━━━
1. 💀 nginx-pod-abc       47 events    kube-system    CrashLoopBackOff
2. 💀 api-server-xyz      23 events    default        CrashLoopBackOff  
3. 💀 coredns-def         19 events    kube-system    CrashLoopBackOff
4. 🔥 worker-ghi          15 events    prod           BackOff
5. 🔥 db-jkl              12 events    prod           BackOff
...

━━━ ACTIONS ━━━
1. Press number (1-9) to jump to pod diagnostic panel
2. Review event message patterns for common root cause
3. Check if pods share same namespace or image

[1-9]=select pod  [Esc]=back to dashboard
```

### Implementation Details

1. **Detect cluster event items**: Check if `AttentionItem.ResourceType == "event"` or `"cluster"`
2. **Create new view handler**: `handleClusterEventDrillDown()`
3. **Parse affected pods** from `AttentionItem.AffectedPods` and `AffectedPodCounts`
4. **Number pods 1-9** for quick keyboard navigation
5. **Allow Enter** on numbered pod to jump to that pod's diagnostic panel

### Files to Modify
- `internal/tui/handlers.go` - Add cluster event Enter handler
- `internal/tui/attention.go` - Add `renderClusterEventPanel()`
- `internal/tui/app.go` - Add ViewClusterEvent view type (optional)

### Success Criteria
- ✅ Pressing Enter on "190× BackOff" shows list of affected pods
- ✅ Can navigate from cluster event → pod list → individual pod diagnostic
- ✅ Maintains simplified navigation (no expansion mode)
- ✅ Keyboard-driven workflow (numbers 1-9 for pod selection)

## Appendix: Design Decisions

### Why Remove External Tools Section?

**Reasoning**: In bundle mode, lnav and kubectl commands are references, not actions. They don't help the immediate diagnosis. Moving to help modal keeps them accessible without cluttering the main panel.

**User Flow**: Operator sees diagnostic panel → realizes they need kubectl → presses '?' → sees kubectl command in help.

### Why Show Only Failing Containers?

**Reasoning**: Healthy containers are noise when debugging a pod failure. The operator needs to focus on what's broken, not what's working.

**Exception**: If ALL containers are healthy but pod is in Error state, show all containers with "⚠️ No failing containers detected - check pod events."

### Why Show Only Warning Events?

**Reasoning**: Normal events ("Scheduled", "Started", "Pulled") describe successful operations. When debugging, we need to see what FAILED, not what succeeded.

**Fallback**: If no Warning events exist, show recent Normal events with note: "No warning events - recent activity shown."

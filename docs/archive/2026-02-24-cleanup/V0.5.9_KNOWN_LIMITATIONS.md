# v0.5.9 Known Limitations

**Version**: v0.5.9 "Simplification"  
**Date**: 2026-01-07  
**Status**: Release Candidate

---

## Navigation Limitation: Cluster Events

### Issue

Dashboard shows aggregated cluster events (e.g., "190× BackOff", "118× Failed") but provides **no way to see which pods are affected**.

### Root Cause

v0.5.9 intentionally removed the expansion feature (►/▼ indicators) to simplify navigation and eliminate display glitches. This removed the pod drill-down capability for cluster event items.

### Affected Items

- Cluster-wide event aggregations (items showing "Warning events" or "cluster" in resource type)
- Example: "190× BackOff" or "118× Failed"

### Current Behavior

```
WARNING:
6. 🔴 190× BackOff    Warning events    cluster     <-- Enter does nothing
7. 🔴 118× Failed     Warning events    cluster     <-- No pod list visible
```

### Workaround

1. Note the event type ("BackOff", "Failed", etc.)
2. Press 'c' to go to classic cluster view
3. Navigate: Clusters → Projects → Namespaces → Pods
4. Look for pods with matching state (CrashLoopBackOff, ImagePullBackOff, etc.)

### Impact

- **High** for large clusters with many failing pods
- **Medium** for smaller clusters (can manually scan pod list)
- **Low** for single-pod failures (already visible as individual items #1-5)

### Planned Fix

**Version**: v0.6.0  
**Solution**: Cluster Events Diagnostic Panel  
**Details**: See `docs/V0.6.0_PLAN.md` Phase 2

Pressing Enter on cluster event items will show:
```
━━━ CLUSTER EVENT: BackOff ━━━
⚠️ 190 occurrences across 12 pods

━━━ AFFECTED PODS ━━━
1. 💀 nginx-pod-abc       47 events    kube-system
2. 💀 api-server-xyz      23 events    default  
3. 💀 coredns-def         19 events    kube-system
...

[1-9]=select pod  [Esc]=back
```

## Container Detection Incomplete

### Issue

Container selector shows current container only, not full container list from pod spec.

### Current Behavior

- Press 'c' in log view → Shows "Container: main (1/1)"
- Cannot cycle through multiple containers in multi-container pods

### Root Cause

Container list is hardcoded to `[]string{currentContainer}` instead of parsing pod spec.

### Workaround

None currently available. Manual kubectl inspection required:
```bash
kubectl describe pod <pod-name> -n <namespace>
```

### Impact

- **High** for multi-container pod debugging
- **Low** for single-container pods (works as expected)

### Planned Fix

**Version**: v0.6.0  
**Solution**: Pod spec parsing  
**Details**: See `docs/V0.6.0_PLAN.md` Phase 3

Implementation:
1. Add `GetPodSpec()` to DataSource interface
2. Parse pod spec JSON/YAML to extract container names
3. Populate full container list in logsMsg

## Non-Issues (Working as Designed)

### Dashboard Expansion Removed

**Not a bug**: The `►/▼` expansion indicators were intentionally removed in v0.5.9.

**Rationale**:
- Reduced complexity (~153 lines removed)
- Eliminated display glitches
- Simplified navigation (direct Enter → diagnostic panel)

**Trade-off**: Lost pod drill-down for cluster events (see above limitation)

## Testing Recommendations

### Before Deploying v0.5.9

1. **Test cluster event navigation** with your typical bundle sizes
2. **Verify pod-specific items work** (items #1-5 in CRITICAL section)
3. **Check container cycling** if you use multi-container pods
4. **Confirm classic view navigation** still works for your workflow

### If Limitations Block Your Workflow

- **Stay on v0.5.8** until v0.6.0 is released
- **Use classic view** ('c' key) for detailed pod inspection
- **Report feedback** to help prioritize v0.6.0 work

## Summary

v0.5.9 is a **simplification release** that trades cluster event expansion for cleaner navigation and fewer bugs. The main limitation (cluster events drill-down) will be addressed in v0.6.0 with a better design.

**Recommendation**: 
- ✅ Deploy v0.5.9 if you primarily debug individual pod failures
- ⏸️ Wait for v0.6.0 if you rely heavily on cluster-wide event analysis
- 📋 Use classic view as workaround if needed
